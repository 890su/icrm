# Решения исполнителя плана 2026-10-31-contacts-core

Формат: решение — почему — цена ошибки. Собрано из журнала исполнения (subagent-driven development).

- Тест слияния на входящие ссылки использует своё поле-связь на `contact` (`holder` из передачи дел ведёт на участие и организацию, а не на контакт) — cost: none.
- Тест NIP при слиянии — организации с разными NIP и выбором `source`: `B` получает NIP `A` без `nip_taken`, потому что `A` архивируется раньше — две живые организации не могут иметь общий NIP — cost: none.
- Слияние получило свою папку фикстур `contacts-merge/` (владеемое поле у контакта через `extend`, поле на `contact`, правило `readonly`) — cost: none.
- Тест «правило видит варианты из `extend`» усилен: правило с `options: {role: [муж]}` и отрицательные случаи — исходный тест плана проходил при любом порядке применения `extend` — cost: none.
- Поле `address` «Монтажа» переименовано в `site_address` **без** `was:`; ослабление правила `was` откачено; спецификация §2.3, §11 и план поправлены — `address` остаётся живым системным полем, и `was: address` перенёс бы адреса организаций; развёрнутых данных нет — cost: в dev-базе значения адреса монтажа теряются.
- Нормализация телефона отклоняет ввод с символами кроме цифр, пробелов и `( ) + - . /`; у почтового домена все части между точками непустые — `libphonenumber-js` вытаскивает номер из любого текста («abc 600100200», «… ext 5»), а `jan@.pl` проходил — cost: none.
- Четвёртая точка поведения `SetBehavior.beforeInsert` (до первой вставки записи) — создание сохраняет сырой ввод до вычисления (дизайн 1b), и сырой NIP упирался бы в уникальный индекс до проверки — cost: на создании проверки NIP и доменов выполняются дважды (лишний запрос).
- Новый преемник при уходе копирует только роль и должность (не `active_from`, не `is_primary`) — спецификация §5.2 называет только их; копия `is_primary` могла бы дать `primary_conflict` — cost: дату начала и «основное» человек ставит сам.
- При слиянии ручные наборы `A`, которых нет у `B`, включаются у `B` первым сохранением вместе со значениями полей, которые есть только в этих наборах; остальные значения пишутся последними, после архивирования `A` — иначе ссылки, требующие такого набора, и `require` этого набора отклоняли законное слияние — cost: лишний `version` у `B` на каждое слияние.
- Схлопнутое основное участие `A` передаёт `is_primary` двойнику у `B`, если у контакта нет другого активного основного — спецификация молчит, роль «основного» сохраняется — cost: none.
- `setLinks` проверяет существование, архив, целевые наборы и циклы только у целей, новых для поля (количество — по всему списку; владеемые поля — полная проверка `link_owned`) — иначе историческая ссылка на архивную запись блокировала слияние и передачу дел; §1.12: при архивировании связи остаются — cost: старая связь на запись, потерявшую целевой набор, остаётся, пока её не изменят.
- Схлопываемое участие с будущим `active_from` закрывается датой начала (`max(today, active_from)`), ошибки шагов слияния несут `recordId` — cost: none.
- Финальная волна исправлений также взяла недорогие мелочи: `phone_region` проверяется `isSupportedCountry`, сопоставление не выдаёт не-организацию за организацию, у почты с архивным владельцем считаются подсказки по домену, README: `B` получает наборы `A` — cost: none.
