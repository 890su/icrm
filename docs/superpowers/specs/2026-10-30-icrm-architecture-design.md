# iCRM — архитектурная спецификация

- **Дата:** 2026-10-30
- **Статус:** утверждена владельцем 2026-10-30
- **Охват:** общая архитектура всей системы + границы подпроектов. Детальный
  план реализации пишется отдельно для каждого подпроекта; первый — «Ядро записей».

---

## 0. Назначение и принципы

### 0.1 Что строим

CRM для работы с клиентами, функционально близкая к Планфиксу, с одним
принципиальным отличием: центральный объект — **Разговор** (тема общения), а не
задача. Клиент звонит, пишет письмо, продолжает в мессенджере — всё это один
текущий разговор. Из разговора рождаются задачи и другие разговоры; к нему
привязаны контакты, контрагент, файлы. Проект — это разговор на одну тему,
у которого включён набор «Проект».

### 0.2 Для кого

Сначала — внутренний инструмент владельца (JDG, IT-услуги: сети, видеонаблюдение,
оборудование), 1–3 пользователя. Затем — возможный SaaS-продукт. Поэтому:
- `workspace_id` есть во всех таблицах с первого дня;
- мультитенантный UI, биллинг, права доступа — **не** делаются, пока не нужны.

### 0.3 Критерии успеха

1. Все клиентские обращения (Email, Telegram, WhatsApp, звонки вручную) попадают
   в разговоры; ни одно не теряется.
2. По каждому открытому разговору без ручных статусов видно, **чей ход**.
3. Новый тип задачи, набор полей или правило добавляется правкой YAML без кода.
4. Сведения «контакт в организации» (учётки, оборудование) хранятся в привязке
   к участию контакта в организации и переживают его уход из фирмы.

### 0.4 Принципы

- **Любая сущность — запись.** Сущности различаются только набором включённых
  наборов полей. Отдельных таблиц под «задачи», «контакты» и т.п. нет.
- **Поведение — в системных наборах.** Код привязывается к системному набору,
  а не к «типу записи».
- **Один язык выражений** для формул, условий правил, фильтров, планировщика,
  отчётов.
- **Хранимые вычисления.** Формулы и итоги хранятся в записи, чтобы по ним
  работали фильтры и индексы.
- **Ошибка конфига — ошибка старта**, а не странное поведение в работе.
- **YAGNI.** Всё, что помечено «позже», в первой версии не строится.

## 1. Модель данных ядра

### 1.1 Понятия

| Понятие | Что это |
|---|---|
| **Workspace** | Рабочее пространство (тенант). Сейчас одно. |
| **Поле** | Определяется **глобально** в библиотеке полей; один ключ — один смысл во всей системе. |
| **Набор полей** | Именованная группа полей + метаданные; системный или пользовательский. |
| **Запись** | Объект с id, заголовком и значениями полей; несёт 0..N включённых наборов. |
| **Связь** | Значение поля-ссылки; хранится в таблице `links`. |
| **Правило** | Условие + эффекты (включить набор, показать/скрыть, обязательность…). |

### 1.2 Поля

Ключ поля — `snake_case` латиницей (`due_date`, `kind`), метка — на русском.
Ключ уникален в workspace. Один и тот же ключ может входить в несколько наборов
(например, `responsible` — в «Задаче» и «Разговоре»), значение у записи одно.

Типы полей:

| Тип | Значение в JSONB | Примечание |
|---|---|---|
| `text` | string | `multiline: true` для длинного текста |
| `number` | number | `precision` |
| `money` | `{amount: string, currency: string}` | amount — десятичная строка, без float |
| `date` | `"YYYY-MM-DD"` | |
| `datetime` | ISO-8601 UTC | |
| `bool` | boolean | |
| `enum` | string / string[] | `options`, `multiple` |
| `user` | user id / id[] | |
| `file` | file id / id[] | |
| `link` | — (в таблице `links`) | `target_sets`, `cardinality: one\|many`, `inverse_label`, `hierarchical`, `owned` (§1.12) |
| `formula` | значение результата | хранимое, см. §1.6 |
| `rollup` | значение результата | хранимое, см. §1.7 |

Системное поле `title` есть у каждой записи.

### 1.3 Наборы полей

```yaml
sets:
  task:
    label: Задача
    system: true            # поведение в коде (см. §3)
    fields: [title, description, conversation, parent_task, responsible,
             due_date, done, done_at, kind]
  montage:
    label: Монтаж
    requires: [task]        # включается только вместе с task
    activation: rule        # manual | rule | both
    fields: [address, warranty_months, act_file, work_cost]
```

- `requires` — наборы, которые обязаны быть включены вместе с этим (включаются
  автоматически).
- `activation` — кто может включать набор: человек, правило или оба.
- Пользовательские наборы (Учётная запись, Оборудование, Монтаж…) кода
  не требуют.

### 1.4 Записи и совмещение наборов

Запись = значения + список включённых наборов. Наборы совмещаются: запись может
быть одновременно «Разговором» и «Проектом», организация — «Клиентом» и
«Поставщиком». Разговор «повышается» до проекта добавлением набора «Проект» —
без копирования и без потери истории.

У каждого включения хранится, **кто его включил**: `manual` или `rule:<rule_id>`.

**Выключение набора не удаляет данные.** Значения полей набора остаются в
записи и скрываются. Если набор включится снова — данные на месте. Поле,
входящее одновременно в другой включённый набор, остаётся видимым.

### 1.5 Связи

- Поле-ссылка задаётся на одной стороне, у него есть `inverse_label`
  (например, `conversation` у задачи → «Задачи» у разговора).
- `target_sets` — какие наборы должны быть у цели (проверяется при сохранении).
- `cardinality: one` — не более одной связи по полю у записи-источника.
- `hierarchical: true` — связь образует дерево (родительская задача,
  родительский разговор); циклы запрещаются при сохранении.
- Связи с собственными данными не делаются: если у связи есть поля, это
  отдельная запись (пример — «Участие в организации», §3.3).
- `owned: true` — связь-владение: цели принадлежат записи-источнику как её
  строки (аналитики), см. §1.12.

### 1.6 Вычисляемые поля (formula)

Значение — выражение над полями **той же записи** (включая другие формулы,
итоги и подстановки):

```yaml
fields:
  work_cost:
    type: formula
    label: Стоимость работ
    expr: '{hours} * {rate}'
  overdue:
    type: formula
    expr: 'IF(AND(NOT({done}), {due_date} < TODAY()), "Просрочено", "В срок")'
```

Тип результата выводится при загрузке конфига; несовпадение типов — ошибка
конфига. Формулы, зависящие от `TODAY()`/`NOW()`, пересчитываются ещё и
ежесуточной фоновой задачей.

### 1.7 Итоговые поля (rollup)

Значение собирается **через поле-ссылку** с других записей:

```yaml
fields:
  tasks_cost_total:
    type: rollup
    label: Сумма по задачам
    via: conversation          # поле-ссылка (или её обратная сторона)
    direction: inverse         # forward | inverse
    field: work_cost
    agg: sum                   # sum count min max avg all any list first
    filter: '{done}'           # необязательно, выражение над связанной записью
```

- `agg: first` = **подстановка** (например, адрес организации в задаче).
- Итог можно собирать с формулы или с другого итога → многоуровневые суммы
  (Проект → подразговоры → задачи) без синтаксиса путей.
- **Рекурсивный итог** по иерархической связи разрешён
  (`total = own + SUM(children.total)`): цикл на уровне определений полей
  допустим только для `hierarchical`-связей, где отсутствие циклов гарантировано
  на уровне записей.

### 1.8 Пересчёт

Значения формул и итогов **хранятся**. При сохранении записи в одной транзакции:

1. Применяются изменённые значения.
2. Цикл до стабилизации (максимум 10 проходов):
   формулы записи → правила (§2) → значения по умолчанию → формулы.
3. По графу зависимостей находятся записи, чьи итоги зависят от изменённых
   полей (через `links`), и пересчитываются по той же схеме — каскадом.
4. Если стабилизация не достигнута — откат и ошибка «правила раскачиваются»
   с перечнем правил.

Граф зависимостей полей строится при загрузке конфига; цикл (кроме §1.7,
рекурсия по иерархии) — ошибка конфига.

Синхронного каскада в транзакции достаточно для целевых объёмов. Фоновая
очередь для каскада вводится только при измеренной проблеме скорости.

### 1.9 Схема БД (ядро)

```sql
workspaces (id uuid pk, name, created_at)

users (id uuid pk, workspace_id, email unique, password_hash, name,
       contact_record_id uuid null, created_at, disabled_at)

records (id uuid pk,            -- uuid v7
         workspace_id, title text,
         data jsonb not null default '{}',   -- значения полей (кроме link)
         version int not null,               -- оптимистичная блокировка
         owner_id uuid null, owner_field text null,  -- строка записи, §1.12
         created_by, created_at, updated_at, archived_at)
  -- GIN (data jsonb_path_ops); выражения-индексы для полей с indexed: true

record_sets (record_id, set_key, enabled_by text, enabled_at,
             pk (record_id, set_key))

links (id uuid pk, workspace_id, field_key, from_id, to_id,
       position int, created_at,
       unique (field_key, from_id, to_id))
  -- индексы (from_id, field_key), (to_id, field_key)

change_log (id bigserial, workspace_id, record_id, user_id null,
            at, kind,  -- value | set | link
            field_key, old jsonb, new jsonb, source text) -- user | rule | cascade | system

files (id uuid pk, workspace_id, record_id null, message_id null,
       name, mime, size, storage_key, created_by, created_at)
```

Таблицы подпроектов 2–4 (идентификаторы, сообщения, доставки, участники) —
в §3–§4.

### 1.10 Конкурентность

- Пользовательское редактирование — оптимистичная блокировка по `version`
  (конфликт → HTTP 409, клиент перечитывает запись).
- Каскад итогов блокирует затронутые записи `SELECT … FOR UPDATE` в порядке
  возрастания id, чтобы избежать взаимоблокировок.

### 1.11 Изменения конфига

- Новое поле/набор — просто появляется.
- Удалённое поле — данные остаются в JSONB, при старте выводится
  предупреждение со списком «осиротевших» ключей.
- Переименование ключа — через `was: old_key` в определении поля; миграция
  данных выполняется при старте один раз.
- Изменилось выражение формулы/итога (хеш определения) — фоновый полный
  пересчёт затронутых полей; до его завершения поле помечено «пересчитывается».

### 1.12 Строки записи (аналитики)

Аналог аналитик Планфикса — повторяющиеся группы полей внутри записи (расходы,
доходы, позиции сметы) — **отдельной сущностью не вводится**. Строка — это
обычная запись со своими наборами, а принадлежность записи-владельцу задаётся
полем-ссылкой с `owned: true`.

```yaml
fields:
  expenses:
    type: link
    label: Расходы
    target_sets: [expense]
    cardinality: many
    owned: true
    inverse_label: Задача
  expenses_total:
    type: rollup
    via: expenses
    field: amount
    agg: sum
  transport_total:                    # итог по виду строки
    type: rollup
    via: expenses
    field: amount
    agg: sum
    filter: '{expense_kind} = "транспортные"'
  task_rate:                          # значение владельца внутри строки
    type: rollup
    via: expenses
    direction: inverse
    field: rate
    agg: first

sets:
  expense:                            # общие поля любого расхода
    label: Расход
    fields: [expense_kind, amount, expense_date, note, task_rate]
  expense_transport:                  # поля по виду — правилом
    requires: [expense]
    activation: rule
    fields: [route, distance_km]

rules:
  - id: transport_fields
    when: '{expense_kind} = "транспортные"'
    enable_set: expense_transport
```

Что строки получают от ядра без нового механизма:
- **разные поля у разных видов строк** — совмещаемые наборы и правила §2;
- **формулы на строку** — §1.6, у каждой строки свои значения;
- **итоги по строкам, в том числе по виду** — §1.7 (`filter`);
- **значения владельца в формуле строки** — обратный итог `agg: first`
  (`task_rate` выше); изменение владельца пересчитывает строки каскадом §1.8;
- **отчёты по строкам всех записей** («расходы статьи X за месяц») — обычные
  фильтры по записям (`HAS_SET("expense")`);
- **справочники** (статья расходов, счёт получателя) — поле-ссылка строки на
  запись-справочник.

Что добавляет `owned: true`:
1. **Один владелец.** У строки ровно одна входящая владеемая связь (по любому
   `owned`-полю). Перепривязать строку к другому владельцу нельзя. Владелец
   хранится ещё и в `records.owner_id` (+ `owner_field`) — для фильтров и
   жизненного цикла; пишется в той же транзакции, что и связь. Строка
   появляется только через пакет `rows` владельца; добавить в владеемое поле
   чужую или самостоятельную запись нельзя (ошибка `link_owned`).
2. **Жизненный цикл.** Архивирование владельца архивирует его строки
   (рекурсивно), связи остаются. Удаление строки (`{id, delete: true}`, прямое
   архивирование строки или исключение её из `PUT …/links/<owned-поле>`) =
   архивирование строки и удаление её из поля-владения.
3. **Пакетное сохранение.** Владелец и его строки (добавить / изменить /
   удалить) сохраняются одной транзакцией с одним каскадом:
   `PATCH /records/:id {version, …, rows: {expenses: [{data, sets?} |
   {id, version, data?} | {id, delete: true}]}}` (то же поле `rows` у
   `POST /records`). Изменённые строки остаются на своих местах, новые
   добавляются в конец в порядке пакета; переставить строки —
   `PUT /records/:id/links/expenses` с тем же набором id. Порядок —
   `links.position`. Каждая изменённая строка проверяет свою `version`.
   Ошибка любой строки откатывает весь пакет; ошибки строки несут
   `row: {field, index}` — поле и номер операции в пакете.
   Правило `readonly` на владеемом поле (по сохранённому состоянию владельца)
   замораживает **состав** строк: добавление, удаление, исключение из
   `PUT …/links` и прямое архивирование строки отклоняются (`readonly`).
   Значения существующих строк при этом подчиняются правилам самой строки.
   Архивирование владельца целиком разрешено. Живая строка в любом
   сохранении (пакетом или прямым `PATCH`) должна сохранять один из
   `target_sets` своего поля (`link_target`).
4. **Видимость.** Строки не попадают в общие списки и поиск: `/query` по
   умолчанию исключает записи с `owner_id`; `includeRows: true` — для отчётов.
   `GET /records/:id` отдаёт строки владеемых полей включённых наборов
   (`rows: {expenses: [...]}`, без вложенных строк). Заголовок строки может
   быть пустым.
5. **Журнал** ведётся у строки; UI показывает его в истории владельца.
6. **Права** (когда появятся) наследуются от владельца.

Ограничения конфига: `owned` несовместим с `hierarchical`; целевые наборы
владеемого поля не должны иметь `system: true` (строка — не разговор и не
контакт). Синтаксический сахар `{owner.field}` вместо обратного итога — позже,
если обратные итоги окажутся неудобны.

## 2. Правила и язык выражений

### 2.1 Язык выражений

Один язык для формул, условий правил, фильтров итогов, фильтров списков,
условий планировщика и отчётов.

- Ссылки на поля: `{field_key}`.
- Литералы: числа, строки в `"…"`, `TRUE`/`FALSE`, даты `DATE("2026-10-30")`.
- Операторы: `+ - * /`, `&` (склейка строк), `= <> < <= > >=`.
- Функции (имена на английском, русские синонимы допустимы):
  `IF/ЕСЛИ`, `AND/И`, `OR/ИЛИ`, `NOT/НЕ`, `IS_EMPTY/ПУСТО`,
  `HAS_SET/ЕСТЬ_НАБОР`, `IN`, `CONTAINS`, `TODAY/СЕГОДНЯ`, `NOW`,
  `DAYS_BETWEEN/ДНЕЙ_МЕЖДУ`, `ADD_DAYS`, `ROUND`, `MIN`, `MAX`, `LEN`,
  `CONCAT`, `COALESCE`.
- Выражение разбирается в AST, типизируется и проверяется при загрузке
  конфига. Произвольного кода нет.
- Пустое значение распространяется предсказуемо: арифметика с пустым → пусто,
  сравнение с пустым → FALSE, `IS_EMPTY` — явная проверка.
- Фильтры, собранные в UI, сохраняются в тот же AST.
- Реализация — в пакете `core`, одинаково работает на сервере и в браузере.

### 2.2 Условия

Условие правила — выражение типа bool **только над полями своей записи**
(включая формулы, итоги, подстановки). Условие по связанной записи делается
через поле-подстановку (`agg: first`).

### 2.3 Эффекты

| Эффект | YAML | Поведение |
|---|---|---|
| Включить набор | `enable_set: montage` | выключается тем же правилом, когда условие ложно; ручные включения правила не трогают |
| Показать / скрыть поле | `show: [...]` / `hide: [...]` | |
| Обязательность | `require: [...]` | сохранение отклоняется с ошибкой по полю |
| Только чтение | `readonly: [...]` | |
| Ограничить варианты | `options: {field: [..]}` | текущее недопустимое значение → ошибка валидации |
| Значение по умолчанию | `default: {field: expr}` | ставится только в пустое поле при срабатывании |
| Проверка | `validate: expr`, `message: "..."` | ложь → ошибка с сообщением |

```yaml
rules:
  - id: montage_by_kind
    when: '{kind} = "montage"'
    enable_set: montage
  - id: act_required_on_done
    when: '{done} AND HAS_SET("montage")'
    require: [act_file]
    readonly: [work_cost]
  - id: dates_order
    when: 'NOT(IS_EMPTY({start})) AND NOT(IS_EMPTY({end}))'
    validate: '{end} >= {start}'
    message: Конец раньше начала
```

Переходы между состояниями («нельзя закрыть без акта») выражаются условной
обязательностью; отдельной машины статусов нет.

### 2.4 Границы

Правила **декларативны**: не создают записи, не отправляют сообщения, не меняют
другие записи. Действия — это **автоматизации** (подпроект 5), использующие
тот же язык условий.

## 3. Системные наборы

К системным наборам можно добавлять пользовательские поля и правила.
Ниже — только то, что зашито в код.

Подробно §3.1–3.3 — в `2026-10-31-contacts-organizations-design.md`
(подпроект 2); ниже — кратко. Системные наборы встроены в пакет `core`;
пользовательский YAML расширяет их секцией `extend` (свои поля, `label`,
`options`), но не может удалить или изменить системные поля.

### 3.1 Контакт (`contact`)

Поля: `title` (ФИО), `notes`, `needs_review`, `merged_into` (служебное).
Поведение:
- **Адреса** (email, телефон, Telegram) — таблица `identities`, не поля.
  Владелец адреса — контакт (личный), его участие в организации (адрес
  в роли) или организация (адрес фирмы без закреплённого человека).
  Адрес уникален среди живых. WhatsApp — не отдельный канал: ищется по
  номеру телефона.
  Нормализация: email — нижний регистр; телефон — E.164; Telegram — числовой id.
- **Слияние дублей** (контакты и организации): перенос адресов, связей,
  участий, строк, значений (конфликты — выбор пользователя), исходная
  запись архивируется с `merged_into`; сообщения переносит шаг подпроекта 3.

### 3.2 Организация (`organization`)

Контрагент: фирма или частный клиент (семья, дом).
Поля: `title`, `org_kind`, `nip` (контрольная сумма, уникален), `address`,
`email_domains` (text, multiple).
Поведение: письмо от незнакомого адреса с доменом из `email_domains`
→ подсказка организации. Держит незакреплённые адреса и вещи, пока их
не заберёт новый человек.

### 3.3 Участие в организации (`membership`)

Поля: `contact` (link one → contact), `organization` (link one → organization),
`role` (enum: ЛПР, бухгалтер, техник, другое; multiple), `position`,
`active_from`, `active_to`, `is_primary`, вычисляемое `is_active`.
Поведение: определение контрагента для нового разговора (§4.3); уход
с передачей дел — адреса и связи переходят преемнику, на организацию,
с человеком или остаются как история.
Учётные записи, оборудование и т.п. — пользовательские наборы со ссылкой
на участие (или на организацию, если это имущество фирмы).

### 3.4 Разговор (`conversation`)

Поля: `title` (тема), `number` (короткий последовательный номер, уникален в workspace), `primary_contact` (link one → contact),
`counterparty` (link one → organization, необязательно),
`responsible` (user), `parent_conversation` (link one, hierarchical),
`related_conversations` (link many), `previous_conversation` (link one),
`closed` (bool), `closed_at`.
Системные служебные поля (заполняются кодом): `last_inbound_at`,
`last_outbound_at` (только сообщения хотя бы одному внешнему адресату),
`last_message_direction`.
Системные итоги: `open_tasks_count` (count задач по `conversation`
с `NOT {done}`), `last_task_done_at` (max `done_at`).

**Ход** (`turn`) — системная формула, проверяется сверху вниз:

| Условие | Значение |
|---|---|
| `{closed}` | Закрыт |
| `{last_message_direction} = "in"` | Наш: ответить |
| `{open_tasks_count} > 0` | Наш: выполнить задачи |
| `NOT(IS_EMPTY({last_task_done_at})) AND (IS_EMPTY({last_outbound_at}) OR {last_task_done_at} > {last_outbound_at})` | Наш: сообщить о выполнении |
| иначе | Ждём клиента |

Внутренние сообщения на `turn` не влияют. `last_message_direction` меняют только входящие (`in`) и исходящие, ушедшие хотя бы одному внешнему адресату (`out`). Зафиксированный вручную звонок (любого направления) считается состоявшимся общением и обновляет поля как `out`.

**Жизненный цикл:**
- Закрытие — вручную или фоновой задачей: разговор в состоянии
  «Ждём клиента» без активности N дней (`auto_close_days`, по умолчанию 14,
  `0` — выключено).
- Новое обращение после закрытия → новый разговор с
  `previous_conversation` → закрытый. Кнопка «перенести в старый»
  (переоткрывает старый, переносит сообщения).

Участники:
```sql
conversation_participants (conversation_id, kind,   -- user | contact
                           user_id null, contact_id null,
                           last_identity_id null,   -- последний канал контакта
                           added_by, added_at)
```
Пользователи-участники видят всё. Контакт становится участником, когда пишет
в разговор или добавлен вручную.

### 3.5 Задача (`task`)

Поля: `title`, `description`, `conversation` (link one → conversation,
необязательно), `parent_task` (link one, hierarchical), `responsible`,
`due_date`, `done` (bool), `done_at` (ставится кодом при `done` → TRUE,
очищается при FALSE), `kind` (enum — типы задач; через правила включает
наборы).

### 3.6 Проект (`project`)

`requires: [conversation]`. Поля: `goal`, `deadline`, `budget`, итоги по
подразговорам и задачам (настраиваются в YAML).
Поведение в UI: дерево подразговоров, сводная лента.

### 3.7 Служебное (не записи)

- **Файлы** (§1.9) — привязаны к записи или сообщению; вложения сообщений
  видны в файлах разговора. Файл с собственными полями → запись с набором
  «Документ» и полем `file`.
- **Пользователи** — вход в систему; могут ссылаться на запись-контакт.

## 4. Сообщения и каналы

### 4.1 Таблицы

```sql
channel_accounts (id, workspace_id, channel, name, config_ref,  -- наш ящик / бот / номер
                  unknown_sender_policy)   -- create_contact | inbox

messages (id uuid pk, workspace_id,
          conversation_id null,            -- null = «Неразобранное»
          direction,                       -- in | out | internal | event
          channel null, channel_account_id null,
          author_user_id null, author_contact_id null, from_identity_id null,
          subject null, body_text, body_html null,
          external_id null, external_thread_ref null, reply_to_external_id null,
          reply_to_message_id null,
          needs_review bool default false,
          sent_at, created_at,
          unique (channel_account_id, external_id))

deliveries (id, message_id, contact_id, identity_id, channel,
            status,   -- pending | sent | delivered | failed
            error null, attempts int, last_attempt_at, external_id null)

message_mentions (message_id, user_id)
```

`event` — звонки (вручную: направление, длительность, заметка) и системные
события ленты.

### 4.2 Адаптеры

Единый интерфейс в `worker`:
```ts
interface ChannelAdapter {
  channel: 'email' | 'telegram' | 'whatsapp';
  start(account, onInbound: (m: InboundMessage) => Promise<void>): Promise<void>;
  send(account, out: OutboundDelivery): Promise<SendResult>;
}
```
`InboundMessage`: аккаунт, внешний id, отправитель (канал + адрес),
получатели, тема, текст/html, вложения, время, `reply_to_external_id`,
ссылки на тред.

Порядок реализации: Email (imapflow IDLE + nodemailer SMTP) → Telegram →
WhatsApp. Режимы Telegram и WhatsApp выбираются в подпроекте 4 (§7).

### 4.3 Входящее: обработка

1. **Приём.** Сохранить сообщение (идемпотентно по `channel_account_id +
   external_id`) до любой обработки.
2. **Отправитель.** Поиск по `identities`.
   - найден → его контакт;
   - не найден и политика аккаунта `create_contact` (по умолчанию для
     мессенджеров) → новый контакт с пометкой «новый, проверить»;
   - не найден и политика `inbox` (по умолчанию для почты) → сообщение
     остаётся в «Неразобранном» (`conversation_id = null`); подсказка
     организации по домену.
3. **Разговор** (первое сработавшее):
   1. ответ на наше сообщение (`reply_to_external_id` / In-Reply-To /
      References) или тег `[iCRM-<n>]` в теме → этот разговор;
      если он закрыт → новый с `previous_conversation`;
   2. у контакта ровно один открытый разговор → он;
   3. несколько открытых → с последней активностью, `needs_review = true`;
   4. нет открытых → новый разговор: тема из темы письма / первых слов,
      `primary_contact`, `counterparty` по участиям (одно активное →
      подставить; несколько → оставить пустым и пометить «выбрать
      контрагента»), `previous_conversation` → последний закрытый разговор
      контакта.
4. Отправитель добавляется в участники; `last_identity_id` обновляется.
5. `last_inbound_at`, `last_message_direction` обновляются через конвейер
   сохранения ядра → пересчёт `turn`.
6. Уведомление ответственному и пользователям-участникам.

`<n>` — поле `number` разговора (§3.4).

### 4.4 Ручные операции

- перенести сообщение в другой разговор;
- выделить выбранные сообщения в новый разговор (ссылка на исходный в
  `related_conversations`);
- объединить два разговора (сообщения, участники, связи; второй архивируется);
- разобрать «Неразобранное»: привязать к контакту/разговору или создать их.

### 4.5 Исходящее и адресаты

- Ответ пишется в разговоре. Список **адресатов** — галочки по
  внешним участникам; по умолчанию отмечен автор сообщения, на которое
  отвечаем (или последний писавший).
- Каждому адресату — своя `delivery` через его `last_identity_id`
  (канал можно сменить вручную).
- Адресаты в email объединяются в одно письмо (первый — To, остальные — Cc);
  мессенджеры — отдельная отправка каждому.
- **Ни одного адресата → `direction = internal`.** Видят только
  пользователи; `@упоминание` пользователя → уведомление.
- Входящее от одного внешнего участника другим не пересылается;
  «переслать копию» — явное действие (новое исходящее с цитатой).
- В исходящих письмах: `In-Reply-To`/`References` последнего письма треда
  и тег `[iCRM-<n>]` в теме.
- Статусы доставки по адресату; `failed` после исчерпания повторов видно
  в ленте с кнопкой «повторить».
- `last_outbound_at` обновляется, когда хотя бы одна доставка ушла
  (`sent`).

## 5. Компоненты, развёртывание, ошибки, тесты

### 5.1 Монорепозиторий (pnpm workspaces, TypeScript)

| Пакет | Ответственность | Зависит от |
|---|---|---|
| `packages/core` | типы полей, язык выражений (парсер, типизатор, вычислитель), движок правил, граф зависимостей, загрузчик и валидатор YAML-конфига. Без I/O | — |
| `packages/db` | схема и миграции Postgres, репозитории, **конвейер сохранения записи и каскад итогов** (общий для server и worker), синхронизация конфига с БД, запросы по фильтрам | core |
| `apps/server` | Fastify HTTP API, вход, маршрутизация сообщений, уведомления, SSE | core, db |
| `apps/worker` | адаптеры каналов, pg-boss задачи (доставки, автозакрытие, суточный пересчёт, пересчёт после смены конфига) | core, db |
| `apps/web` | React + Vite SPA; формы из наборов и правил через `core` | core |
| `config/` | YAML наборов, полей, правил workspace | — |

API (первая версия, REST + JSON): `/meta` (скомпилированный конфиг для web),
`/records` (CRUD, наборы), `/records/:id/links`, `/query` (фильтр-AST,
сортировка, пагинация), `/conversations/:id/messages`, `/messages/:id/deliveries`,
`/inbox` (неразобранное), `/events` (SSE).

### 5.2 Инфраструктура

- Docker Compose на srv-150: `postgres` (свой контейнер pg16), `server`,
  `worker`, статика `web` через server.
- Порты только на `127.0.0.1`, наружу — Cloudflare Tunnel. Домен — при
  развёртывании.
- Очередь — pg-boss (в той же БД).
- Файлы — том на srv-150 за интерфейсом `FileStorage` (позже S3).
- Вход — email + пароль (argon2), серверные сессии; опционально Cloudflare
  Access поверх.
- Секреты (пароли ящиков, токены ботов) — только через env/secret store,
  в `channel_accounts.config_ref` хранится ссылка.

### 5.3 Ошибки

- Конвейер сохранения атомарен; ошибки структурные:
  `{field, rule_id?, code, message}`.
- Ошибка конфига — сервер не стартует, отчёт: файл, путь в YAML, причина.
- Входящие сохраняются до обработки; сбой маршрутизации → сообщение
  в «Неразобранном» с `needs_review`, а не потеря.
- Доставки: повторы с экспоненциальной паузой (5 попыток), затем `failed`.
- Журнал изменений `change_log` для каждого изменения значения, набора,
  связи с источником (`user | rule | cascade | system`).

### 5.4 Тестирование (TDD)

- `core` — модульные тесты Vitest: разбор и типизация выражений, пустые
  значения, правила и стабилизация, обнаружение раскачки, каскад итогов,
  рекурсивные итоги по иерархии, циклы в конфиге, миграция `was:`.
- `db`/`server` — интеграционные тесты на реальном Postgres (Docker):
  конвейер сохранения, каскад в транзакции, оптимистичная блокировка,
  маршрутизация входящих по всем веткам §4.3.
- адаптеры — контрактные тесты на сохранённых образцах писем и вебхуков.
- `web` — несколько сквозных сценариев Playwright, когда появится UI.

## 7. Вне первой версии и открытые вопросы

**Не делаем сейчас:**
- права доступа и роли (все пользователи видят всё);
- визуальный конструктор наборов и правил;
- SIP-интеграция (звонки — вручную);
- ИИ-маршрутизация и саммари разговоров;
- мобильное приложение;
- мультитенантный UI / регистрация компаний;
- фоновая очередь для каскада итогов.

**Открытые вопросы (решаются в своих подпроектах):**
1. Telegram: бот или личный аккаунт (MTProto) с фильтром клиентских чатов — подпроект 4.
2. WhatsApp: официальный Cloud API или неофициальный шлюз — подпроект 4.
3. Домен развёртывания — при первом деплое.
4. Шаблоны документов: формат (DOCX-шаблоны / HTML→PDF) — подпроект 6.
