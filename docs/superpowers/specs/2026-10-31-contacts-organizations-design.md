# iCRM — подпроект 2 «Контакты и организации»

Дата: 2026-10-31. Уточняет §3.1–3.3 и §6 основной спецификации
(`2026-10-30-icrm-architecture-design.md`); при расхождении действует этот документ.

Подпроект делится на две части с одной спецификацией и двумя планами:

| Часть | Содержание | Зависит от |
|---|---|---|
| **2a — основа** | системные наборы и `extend`, адреса (identities), сопоставление, участия и передача дел, слияние дублей | 1, 1b |
| **2b — добавки** | подсказка дублей, заполнение по NIP, импорт vCard / CSV / XLSX | 2a |

Подпроект 3 «Разговоры» зависит только от 2a.

---

## 1. Назначение

- По адресу любого канала однозначно находится, **кто** пишет и **от какой
  организации** (§4.3 основной спецификации).
- Сведения «контакт в организации» (адреса, учётки, оборудование) привязаны
  к участию, переживают уход человека и передаются преемнику или остаются
  за организацией (критерий успеха §0.3 п.4).
- Дубли контактов и организаций сливаются без потерь.
- Частный клиент (семья, дом) — такой же контрагент, как фирма.

Вне подпроекта: сообщения, разговоры, каналы, интерфейс.

## 2. Системные наборы

### 2.1 Откуда берутся

Системная часть конфига поставляется пакетом `core` (YAML внутри пакета).
Загрузчик разбирает её первой тем же парсером под именем файла `<system>`,
затем пользовательские `config/*.yaml`, и компилирует всё вместе.

Системные поля и наборы помечены как системные. В пользовательском YAML
**нельзя** (ошибка старта):
- объявить поле или набор с системным ключом;
- поменять тип системного поля, `target_sets`, `cardinality`, `multiple`,
  выражение формулы;
- убрать системное поле из системного набора;
- сделать системный набор целью `owned`-связи (уже запрещено в 1b).

Пользовательский YAML **может** — новая секция `extend`:

```yaml
extend:
  sets:
    contact: {fields: [birthday]}            # добавить свои поля в системный набор
    membership: {fields: [extension_number]}
  fields:
    role: {options: [ЛПР, бухгалтер, техник, муж, жена, сын, дочь, другое]}
    org_kind: {label: Тип клиента}           # только label и options
```

- `extend.sets.<set>.fields` — дописываются к полям системного набора
  (поле должно быть объявлено в `fields`). Расширять можно только системные
  наборы; свои наборы правятся напрямую.
- `extend.fields.<field>` — только `label` и `options` (для `enum`).
  `options` заменяют список целиком. Код не опирается на конкретные варианты.
- Правила могут ссылаться на системные поля и наборы, включать
  пользовательские наборы на контактах и организациях, делать системные поля
  обязательными (`require: [nip]` при `{org_kind} = "фирма"`).
- Пользовательские связи могут вести на системные наборы
  (`holder: {type: link, target_sets: [membership, organization]}`).

**Служебные поля** (`managed`) заполняет только код; запись такого поля
через API — ошибка `managed_field`. Атрибут `managed` допустим только
в системной части.

Поведение системных наборов (проверки и побочные действия при сохранении)
подключается к конвейеру сохранения записи как обработчики набора; ядро
вызывает их для записей, у которых набор включён.

### 2.2 `contact` — человек

| Поле | Тип | Примечание |
|---|---|---|
| `title` | — | ФИО |
| `notes` | text, multiline | |
| `needs_review` | bool | «новый, проверить»: ставит канал при автосоздании контакта (подпроект 4); человек снимает |
| `merged_into` | link one → contact, organization | `managed`; заполняется при слиянии (§6). Одно поле на оба набора; цель — всегда запись того же вида |

### 2.3 `organization` — контрагент (фирма или частный клиент)

| Поле | Тип | Примечание |
|---|---|---|
| `title` | — | название или «Ковальские, ul. Długa 5» |
| `org_kind` | enum | варианты по умолчанию: `фирма`, `частный клиент`; меняются через `extend` |
| `nip` | text | нормализуется до 10 цифр, проверяется контрольная сумма (`nip_invalid`); уникален среди живых записей (`nip_taken` с указанием владельца) |
| `address` | text, multiline | |
| `email_domains` | text, multiple | нижний регистр, без `@`; публичные почтовые домены (`gmail.com`, `wp.pl`, `o2.pl`, `onet.pl`, `interia.pl`, `outlook.com`, `hotmail.com`, `yahoo.com`, `icloud.com`, `proton.me`…) запрещены (`public_domain`) — список в коде |
| `merged_into` | — | то же поле, что у `contact` (§2.2) |

Семья или дом частного клиента — запись `organization` с `org_kind =
"частный клиент"`; члены семьи — участия с ролями «муж», «жена» и т.д.
Оборудование на объекте клиента ссылается на эту запись.

Поле `address` у набора «Монтаж» в стартовом `config/tasks.yaml`
переименовывается в `site_address` (`was: address`): один ключ — один смысл.

### 2.4 `membership` — участие контакта в организации

| Поле | Тип | Примечание |
|---|---|---|
| `title` | — | при создании с пустым заголовком код ставит «<контакт> — <организация>» |
| `contact` | link one → contact | обязательно |
| `organization` | link one → organization | обязательно |
| `role` | enum, multiple | варианты по умолчанию: `ЛПР`, `бухгалтер`, `техник`, `другое` |
| `position` | text | должность |
| `active_from` | date | |
| `active_to` | date | пусто — действует |
| `is_primary` | bool | основное участие контакта |
| `is_active` | formula | `IS_EMPTY({active_to}) OR {active_to} >= TODAY()` |

Ограничения при сохранении (ошибка по полю):
- `contact` и `organization` заполнены (`required`);
- у пары «контакт + организация» не больше одного активного участия
  (`membership_active_exists`); уйти и вернуться — второе участие;
- у контакта не больше одного активного участия с `is_primary`
  (`primary_conflict`);
- `active_to >= active_from`, если заполнены оба.

Сохранение участия блокирует запись контакта (`FOR UPDATE`), чтобы две
параллельные правки не обошли ограничения.

Хранимое `is_active` с `TODAY()` пересчитывается суточной задачей (бэклог);
код сопоставления и проверки ограничений не полагаются на хранимое значение
и сравнивают `active_to` с текущей датой workspace сами.

## 3. Адреса (identities)

### 3.1 Таблица

```sql
identities (id uuid pk, workspace_id,
            owner_id uuid not null references records,  -- contact | membership | organization
            channel text not null,          -- email | phone | telegram
            address_normalized text not null,
            address_display text not null,
            label text null,                -- «рабочий», «домашний»…
            verified bool not null default false,
            created_at, archived_at null)
  unique (workspace_id, channel, address_normalized) where archived_at is null
  index (owner_id)
```

**Владелец** — живая запись с набором `contact`, `membership` или
`organization` (иначе `invalid_owner`):
- контакт — личный адрес, уходит вместе с человеком;
- участие — адрес человека в роли («телефон бухгалтера Firma X»);
- организация — адрес фирмы без закреплённого человека (общий ящик,
  номер ушедшего сотрудника до назначения нового).

### 3.2 Нормализация (пакет `core`, чистые функции)

| Канал | Нормализация | Ошибка |
|---|---|---|
| `email` | обрезка пробелов, нижний регистр; должен содержать один `@` и непустые части | `invalid_address` |
| `phone` | E.164 через `libphonenumber-js`; страна по умолчанию — `workspace.phone_region` (новый ключ конфига, по умолчанию `PL`) | `invalid_address` |
| `telegram` | числовой id → строка цифр; `@username` → `@` + нижний регистр | `invalid_address` |

- **WhatsApp — не отдельный канал**: его идентификатор — номер телефона.
  Поиск с каналом `whatsapp` идёт по `phone`.
- Telegram `@username` хранится, пока человек не напишет; подпроект 4 при
  первом входящем с совпадающим username заменяет адрес на числовой id.
- `address_display` — как ввёл человек (или как пришло из канала).

### 3.3 Жизненный цикл

- Адрес не удаляется, а архивируется (`archived_at`); на него будут ссылаться
  сообщения подпроекта 4. Архивный адрес не мешает добавить тот же адрес
  другому владельцу.
- Архивирование владельца архивирует его живые адреса. Закрытое участие
  (с `active_to`) не архивируется — его адреса работают, пока их не передадут
  (§5).
- Добавление, перенос, архивирование адреса пишется в `change_log` новым видом
  `identity` у затронутых записей (старый и новый владелец):
  `old`/`new` = `{identityId, channel, address}`.
- Одновременное добавление одного адреса двумя запросами упирается в
  уникальный индекс; нарушение (23505) превращается в `identity_taken`.

### 3.4 API

| Метод | Назначение |
|---|---|
| `POST /records/:id/identities` `{channel, address, label?, verified?}` | добавить адрес владельцу |
| `PATCH /identities/:id` `{label?, verified?, display?}` | правка подписи и отображения |
| `POST /identities/:id/move` `{to}` | перенести на другого владельца |
| `DELETE /identities/:id` | архивировать |
| `GET /identities?q=` | поиск по части нормализованного или отображаемого адреса, до 20 результатов, с владельцами |
| `GET /identities/lookup?channel=&address=` | `resolveAddress` (§4) |

`identity_taken` возвращает текущего владельца (`ownerId`, `ownerTitle`),
чтобы интерфейс предложил «перенести».

`GET /records/:id` у записей с `contact`, `membership`, `organization`
дополнительно возвращает `identities` (живые). У контакта — `memberships`
(активные и закрытые, с организацией), у организации — `memberships`
(с контактом).

## 4. Сопоставление

Функции `packages/db`; подпроект 4 вызывает их для каждого входящего.

**`resolveAddress(ws, channel, address)`** — нормализует адрес
(`whatsapp` → `phone`; неразборчивый — `invalid_address` без поиска), ищет
живой адрес и возвращает:

| Владелец адреса | Результат |
|---|---|
| контакт | `{identity, contact, membership: null, organization: counterpartyOf(contact)}` |
| участие | `{identity, contact: участник, membership, organization: организация участия, membershipEnded}` — `membershipEnded = true`, если участие закрыто |
| организация | `{identity, contact: null, membership: null, organization}` |
| не найден | `{identity: null, contact: null, organization: null, hints}` |

`hints` — только для email: живые организации, у которых домен адреса есть
в `email_domains` (может быть несколько).

**`counterpartyOf(contact)`** — по активным участиям контакта:
- одно → его организация;
- несколько → организация участия с `is_primary`, если оно есть;
- иначе → `null` (вызывающий помечает «выбрать контрагента», §4.3).

## 5. Уход из организации и передача дел

### 5.1 Предпросмотр

`GET /memberships/:id/handover` — что висит на участии:
- `identities` — живые адреса участия;
- `links` — связи, ведущие на участие из других записей (учётки,
  оборудование — любые поля, чьи `target_sets` включают `membership`), с
  заголовком записи-источника, полем и признаком, допускает ли поле
  организацию как цель (`organizationAllowed`).

### 5.2 Операция

`POST /memberships/:id/end`

```json
{ "date": "2026-11-30",
  "successor": { "membershipId": "…" }
             | { "contactId": "…", "role": ["…"], "position": "…" }
             | null,
  "identities": { "<identityId>": "successor" | "organization" | "contact" | "keep" | "archive" },
  "links":      { "<linkId>": "successor" | "organization" | "keep" } }
```

Одна транзакция:
1. Участию ставится `active_to = date` (уже закрытое — ошибка
   `membership_ended`).
2. Преемник: существующее участие — должно быть активным и в той же
   организации; либо создаётся новое участие для `contactId` (роль и
   должность по умолчанию — с уходящего участия).
3. Адреса участия:
   - `successor` — к участию преемника (номер остаётся у фирмы, за новым человеком);
   - `organization` — на организацию (номер у фирмы, человек не назначен);
   - `contact` — на контакт уходящего (забирает с собой);
   - `keep` — остаются на закрытом участии (`membershipEnded` при сопоставлении);
   - `archive` — архивируются.
4. Связи на участие:
   - `successor` — перевешиваются на участие преемника;
   - `organization` — на организацию (только если поле допускает организацию);
   - `keep` — остаются как история.

   Перевешивание выполняется сохранением записи-источника через обычный
   конвейер: её правила, `readonly`, `cardinality`, итоги и каскад работают
   как при ручной правке.
5. Значения по умолчанию для элементов, не названных в запросе: при
   преемнике — `successor`; без преемника — `organization` для адресов и для
   связей, чьё поле допускает организацию, иначе `keep`.

Ошибки: `successor`/`organization` там, где недопустимо, — `handover_target_invalid`
с указанием элемента. Отказ правила записи-источника откатывает всю операцию;
ошибка указывает запись и поле.

### 5.3 Незакреплённое у организации

- `GET /organizations/:id/unassigned` — адреса, принадлежащие организации,
  и связи, ведущие на неё из полей, которые допускают и `membership`
  (то, что можно закрепить за человеком).
- `POST /memberships/:id/take` `{identities: [id…], links: [id…]}` — забрать
  выбранное на это участие (активное, той же организации) одной транзакцией;
  связи перевешиваются так же, как в §5.2.

Человек, перешедший в другую фирму, — две операции: закрыть старое участие
и создать новое.

## 6. Слияние дублей

Сливаются записи одного системного вида: контакт с контактом, организация
с организацией (иначе `merge_kind_mismatch`; сама с собой — `merge_self`;
архивная — `merge_archived`). Слияние `A → B` необратимо: `A`
архивируется с `merged_into = B`, история — в `change_log`.

### 6.1 Предпросмотр

`GET /records/:a/merge-preview?into=:b`:
- `conflicts` — поля, где у обоих разные непустые значения (связи
  `cardinality: one` тоже), с обоими значениями;
- что переедет: адреса, участия, связи, строки;
- какие участия схлопнутся (§6.2 п.3).

### 6.2 Операция

`POST /records/:a/merge` `{into: b, values: {<field>: "source" | "target"}}`

Одна транзакция; `A`, `B` и затронутые участия блокируются в порядке id.
1. **Значения.** Конфликт — по выбору, по умолчанию `target`. Пустые поля `B`
   заполняются из `A`. Наборы `A` включаются у `B` (`enabled_by` сохраняется).
2. **Адреса** `A` переходят к `B`.
3. **Участия.** Контакты: участия с `contact = A` перевешиваются на `B`.
   Организации: участия с `organization = A` — на `B`. Если у пары
   «контакт + организация» оказалось два активных участия, они
   схлопываются: остаётся участие, которое было у `B`; адреса и связи
   участия от `A` переходят на него, роли объединяются, участие от `A`
   закрывается текущей датой и архивируется. Если
   после переноса у контакта два `is_primary`, флаг остаётся у участия `B`.
4. **Связи на `A`** из любых записей перевешиваются на `B` сохранением
   записи-источника (как в §5.2). Если источник уже ссылается на `B` по тому
   же полю — связь на `A` снимается.
5. **Связи и строки `A`** (поля-ссылки самой `A`, `owned`-строки) переходят
   к `B`; для `cardinality: one` с заполненными обеими сторонами действует
   выбор из п.1.
6. Пользователи с `contact_record_id = A` переходят на `B`.
7. `A` архивируется с `merged_into = B`. Уникальность NIP проверяется после
   архивирования `A`, поэтому одинаковый NIP слиянию не мешает.
8. **Шаги следующих подпроектов.** Слияние вызывает список `MergeStep`
   (`(tx, kind, sourceId, targetId) => Promise<void>`); подпроект 3 добавит
   перенос сообщений и участников разговоров. В 2a список пуст.

Отказ правила любой сохраняемой записи откатывает всё слияние; ошибка
указывает запись и поле.

## 7. Подпроект 2b

### 7.1 Подсказка дублей

Расширения Postgres `pg_trgm` и `unaccent` (есть в `postgres:16`).
Нормализация имени: нижний регистр, без диакритики, без знаков препинания,
слова отсортированы; у организаций дополнительно отброшены правовые формы
(`sp. z o.o.`, `s.a.`, `s.c.`, `sp.j.`, `sp.k.`, `spółka cywilna`,
`jdg` и т.п. — список в коде).

Кандидаты (только живые записи, без пар из `duplicate_dismissals`):
- **контакты:** совпадает нормализованное ФИО; или триграммное сходство
  ≥ 0.6 и есть общая организация (по участиям, в т.ч. закрытым) или общий
  почтовый домен адресов (кроме публичных);
- **организации:** сходство нормализованного названия ≥ 0.7; или общий
  домен в `email_domains`; или совпадает нормализованный `address`.

API:
- `GET /records/:id/duplicates` — кандидаты к записи с причинами;
- `GET /duplicates?set=contact|organization&limit=&offset=` — пары
  с причинами;
- `POST /duplicates/dismiss` `{a, b}` — «не дубль»
  (`duplicate_dismissals (workspace_id, a_id, b_id, created_by, created_at)`,
  пара хранится упорядоченной);
- ответ `POST /records` для контакта или организации содержит
  `possibleDuplicates` (подсказка, сохранение не блокируется).

### 7.2 Заполнение по NIP

Источник — «белый список» VAT Минфина (`wl-api.mf.gov.pl`): без ключа.
Клиент в `apps/server` за интерфейсом `NipRegistry`; тесты используют
подделку и не ходят в сеть.

Новые поля `organization`: `regon` (text), `krs` (text), `vat_status`
(enum: `czynny`, `zwolniony`, `niezarejestrowany`), `bank_accounts`
(text, multiple), `registry_checked_at` (datetime, `managed`).

- `GET /registry/nip/:nip` — данные реестра без сохранения
  (`nip_invalid`, `nip_not_found`).
- `POST /records/:id/registry-refresh` — записать в организацию через
  конвейер сохранения: `title` и `address` — только если пусты; `regon`,
  `krs`, `vat_status`, `bank_accounts`, `registry_checked_at` —
  перезаписываются.
- Реестр недоступен или ответил ошибкой — 502 `registry_unavailable`.
- У сервиса суточный лимит запросов: вызов только по действию человека,
  массовых проверок нет. GUS BIR (нужен ключ) — бэклог.

### 7.3 Импорт

Форматы: vCard 3.0/4.0 (`.vcf`), CSV, XLSX (первый лист, `exceljs`).
CSV: разделитель `;` или `,` определяется по первой строке; кодировка UTF-8
(с BOM или без), а если файл не декодируется как UTF-8 — Windows-1250.
Первая строка CSV/XLSX — заголовки. Лимиты: файл до 5 МБ, до 5000 строк
(`import_too_large`). Файл не сохраняется.

**Сопоставление колонок.** vCard — фиксированное: `FN` (или `N`) → ФИО,
`TEL` → phone, `EMAIL` → email, `ORG` → организация, `TITLE` → должность,
`NOTE` → заметки. CSV/XLSX — задаётся в запросе: колонка →
`contact.title` | `contact.<поле>` | `identity.email` | `identity.phone` |
`identity.telegram` | `organization.title` | `organization.nip` |
`organization.<поле>` | `membership.role` | `membership.position` | `skip`.
В одной ячейке адреса может быть несколько значений через `,` или `;`.

**Действие по строке:**
1. Адреса нормализуются; неразборчивые — предупреждение, адрес пропускается.
2. Контакт ищется по любому адресу строки. Адреса ведут к разным
   контактам → строка пропускается (`ambiguous_match`). Найден → обновить:
   пустые поля дозаполняются, новые адреса добавляются. Не найден и есть
   ФИО или адрес → создать. Ни того ни другого → пропустить (`empty_row`).
3. Организация: по NIP, иначе по точному нормализованному названию, иначе
   создаётся.
4. Участие контакт ↔ организация создаётся, если активного нет; роль и
   должность — из строки.

**API (multipart: файл + JSON `mapping`):**
- `POST /import/preview` — пробный прогон без записи: по каждой строке
  действие (`create` | `update` | `skip`), причина и предупреждения;
- `POST /import/commit` — то же с записью; каждая строка — своя
  транзакция, ошибка строки не останавливает остальные; ответ — отчёт
  по строкам. Повторный импорт того же файла не создаёт дублей (всё
  находится по адресам и NIP).

## 8. Схема и миграции

- **`003_contacts` (2a):** `identities` с индексами (§3.1); вид `identity`
  в `change_log.kind`; частичный уникальный индекс
  `(workspace_id, (data->>'nip')) where archived_at is null and data ? 'nip'`.
- **`004_duplicates` (2b):** `create extension pg_trgm, unaccent`;
  неизменяемая обёртка над `unaccent` для индексов; `duplicate_dismissals`;
  триграммный индекс по нормализованному заголовку записей.

## 9. Ошибки

Формат прежний: `{field?, code, message}` (+ `row` у импорта).
Новые коды: `invalid_address`, `identity_taken`, `invalid_owner`,
`nip_invalid`, `nip_taken`, `nip_not_found`, `public_domain`,
`membership_active_exists`, `primary_conflict`, `membership_ended`,
`handover_target_invalid`, `merge_kind_mismatch`, `merge_self`,
`merge_archived`, `managed_field`, `registry_unavailable`,
`import_too_large`, `ambiguous_match`, `empty_row`.

## 10. Тестирование

- **`core`:** нормализация телефонов (PL и иностранные, пробелы, скобки,
  `00`/`+`), email, Telegram; контрольная сумма NIP; сборка «система +
  `extend`» и все запреты §2.1; `managed`; нормализация ФИО и названий.
- **`db`** (реальный Postgres): уникальность, гонка и архивирование адресов;
  все ветки `resolveAddress` и `counterpartyOf`; ограничения участий;
  передача дел со всеми вариантами и откат при отказе правила источника;
  `take`; слияние контактов и организаций (схлопывание участий, связи,
  строки, NIP, пользователи); кандидаты в дубли; сопоставление импорта.
- **`server`:** маршруты; подделка `NipRegistry`; разбор образцов: vCard 3.0
  и 4.0, CSV с `;` и `,`, CSV в Windows-1250, XLSX.
