# Decisions: iCRM

> Key decisions made during work. Appended as they happen.

## 2026-10-30 — Project created
**What:** Created `icrm` as `umbrella` (7 подпроектов).
**Why:** Своя CRM с разговором в центре; подсистемы независимы и идут отдельными циклами spec → plan → code.
**Affected:** CONTEXT.md, PLAN.md, ROADMAP.md

## 2026-10-30 — Центральный объект — Разговор
**What:** Разговор = тема общения с человеком (и контрагентом), сквозная по каналам. Новое обращение после закрытия — новый разговор со ссылкой на прошлый.
**Why:** Работа начинается с общения; задачи — следствие разговора.
**Boundary:** Задачи могут существовать и без разговора (внутренние).

## 2026-10-30 — Универсальная запись с совмещаемыми наборами полей
**What:** Любая сущность — запись; тип определяется набором включённых наборов полей; наборы совмещаются; системные наборы несут поведение в коде.
**Why:** «Любая сущность отличается от другой просто набором полей». Разговор превращается в проект добавлением набора, без конвертации.
**Boundary:** Сообщения, файлы, доставки, журнал — служебные таблицы, не записи.

## 2026-10-30 — Своё ядро TS + Postgres, конфиг YAML
**What:** Свой стек (не Twenty, не Directus); наборы/поля/правила в YAML в git, визуальный конструктор позже.
**Why:** Модель совмещаемых наборов не ложится на объектные модели готовых CRM/low-code.
**Affected:** весь проект

## 2026-10-30 — Конвейер сохранения записи живёт в packages/db
**What:** Сохранение записи, каскад итогов, синхронизация конфига и фильтры→SQL — в `packages/db` (`RecordService`), а не в `apps/server`.
**Why:** Worker (каналы) тоже сохраняет записи и не должен зависеть от HTTP-сервера.
**Affected:** spec §5.1, plan 2026-10-30-core-records

## 2026-10-30 — Семантика движка записи (уточнения к спецификации)
**What:** Формулы/итоги считаются только для полей включённых наборов; `readonly` проверяется по состоянию до правки; проверка типа/вариантов — только для изменённых ключей; поле из `show` скрыто по умолчанию; агрегаты пустого множества: sum/count 0, all TRUE, any FALSE, list [], прочие null; архивные записи в итоги не входят.
**Why:** Без этого глобальная библиотека полей заставила бы каждую запись считать все формулы, а правка конфига «замораживала» бы старые записи.
**Affected:** plan 2026-10-30-core-records (Tasks 6, 7, 10, 11)

## 2026-10-30 — Вход в API подпроекта 1 — статический токен
**What:** `ICRM_API_TOKEN` + системный пользователь `system@local`; логин с паролем — в подпроекте 7.
**Why:** API в подпроекте 1 слушает только 127.0.0.1; UI ещё нет.

## 2026-10-31 — Аналитики = строки-записи через связь-владение
**What:** Аналог аналитик Планфикса (повторяющиеся группы полей в задаче: расходы, доходы) — не отдельная сущность. Строка — обычная запись со своими наборами; принадлежность задаётся полем-ссылкой `owned: true` (один владелец, общий жизненный цикл, пакетное сохранение, скрыта из общих списков). Разные поля у видов строк — правила включения наборов; итоги по виду — `filter` итога; значения владельца в строке — обратный итог `agg: first`.
**Why:** Одно ядро (формулы, правила, итоги, фильтры→SQL, журнал) работает и для записей, и для строк; отчёты по аналитикам всех задач — обычные фильтры. Хранение строк массивом в JSONB потребовало бы второго измерения во всём ядре.
**Boundary:** Реализуется отдельным подпроектом 1b после «Ядра записей»; сахар `{owner.field}` — позже, по необходимости.
**Affected:** spec §1.2, §1.5, §1.9, §1.12, §6

## 2026-10-31 — Postgres ≥ 16
**What:** Минимальная версия Postgres — 16 (фильтры используют `pg_input_is_valid`; dev compose и тесты — `postgres:16-alpine`, кодировка UTF-8, ctype `C.UTF-8`).
**Why:** Безопасная проверка дат/времени в SQL-фильтрах без исключений на кривых данных; `lower()` по кириллице совпадает с `evaluate` только при UTF-8 ctype.
**Affected:** packages/db/src/query.ts, docker-compose.dev.yml
