# Decisions: iCRM

> Key decisions made during work. Appended as they happen.

## 2026-10-30 — Project created
**What:** Created `icrm` as `umbrella` (7 подпроектов).
**Why:** Своя CRM с разговором в центре; подсистемы независимы и идут отдельными циклами spec → plan → code.
**Affected:** CONTEXT.md, PLAN.md, ROADMAP.md

## 2026-10-30 — Центральный объект — Разговор
**What:** Разговор = тема общения с человеком (и контрагентом), сквозная по каналам. Новое обращение после закрытия — новый разговор со ссылкой на прошлый.
**Why:** Работа начинается с общения; задачи — следствие разговора.
**Boundary:** Задачи могут существовать и без разговора (внутренние).

## 2026-10-30 — Универсальная запись с совмещаемыми наборами полей
**What:** Любая сущность — запись; тип определяется набором включённых наборов полей; наборы совмещаются; системные наборы несут поведение в коде.
**Why:** «Любая сущность отличается от другой просто набором полей». Разговор превращается в проект добавлением набора, без конвертации.
**Boundary:** Сообщения, файлы, доставки, журнал — служебные таблицы, не записи.

## 2026-10-30 — Своё ядро TS + Postgres, конфиг YAML
**What:** Свой стек (не Twenty, не Directus); наборы/поля/правила в YAML в git, визуальный конструктор позже.
**Why:** Модель совмещаемых наборов не ложится на объектные модели готовых CRM/low-code.
**Affected:** весь проект

## 2026-10-30 — Конвейер сохранения записи живёт в packages/db
**What:** Сохранение записи, каскад итогов, синхронизация конфига и фильтры→SQL — в `packages/db` (`RecordService`), а не в `apps/server`.
**Why:** Worker (каналы) тоже сохраняет записи и не должен зависеть от HTTP-сервера.
**Affected:** spec §5.1, plan 2026-10-30-core-records

## 2026-10-30 — Семантика движка записи (уточнения к спецификации)
**What:** Формулы/итоги считаются только для полей включённых наборов; `readonly` проверяется по состоянию до правки; проверка типа/вариантов — только для изменённых ключей; поле из `show` скрыто по умолчанию; агрегаты пустого множества: sum/count 0, all TRUE, any FALSE, list [], прочие null; архивные записи в итоги не входят.
**Why:** Без этого глобальная библиотека полей заставила бы каждую запись считать все формулы, а правка конфига «замораживала» бы старые записи.
**Affected:** plan 2026-10-30-core-records (Tasks 6, 7, 10, 11)

## 2026-10-30 — Вход в API подпроекта 1 — статический токен
**What:** `ICRM_API_TOKEN` + системный пользователь `system@local`; логин с паролем — в подпроекте 7.
**Why:** API в подпроекте 1 слушает только 127.0.0.1; UI ещё нет.

## 2026-10-31 — Аналитики = строки-записи через связь-владение
**What:** Аналог аналитик Планфикса (повторяющиеся группы полей в задаче: расходы, доходы) — не отдельная сущность. Строка — обычная запись со своими наборами; принадлежность задаётся полем-ссылкой `owned: true` (один владелец, общий жизненный цикл, пакетное сохранение, скрыта из общих списков). Разные поля у видов строк — правила включения наборов; итоги по виду — `filter` итога; значения владельца в строке — обратный итог `agg: first`.
**Why:** Одно ядро (формулы, правила, итоги, фильтры→SQL, журнал) работает и для записей, и для строк; отчёты по аналитикам всех задач — обычные фильтры. Хранение строк массивом в JSONB потребовало бы второго измерения во всём ядре.
**Boundary:** Реализуется отдельным подпроектом 1b после «Ядра записей»; сахар `{owner.field}` — позже, по необходимости.
**Affected:** spec §1.2, §1.5, §1.9, §1.12, §6

## 2026-10-31 — Postgres ≥ 16
**What:** Минимальная версия Postgres — 16 (фильтры используют `pg_input_is_valid`; dev compose и тесты — `postgres:16-alpine`, кодировка UTF-8, ctype `C.UTF-8`).
**Why:** Безопасная проверка дат/времени в SQL-фильтрах без исключений на кривых данных; `lower()` по кириллице совпадает с `evaluate` только при UTF-8 ctype.
**Affected:** packages/db/src/query.ts, docker-compose.dev.yml

## 2026-10-31 — Строки записи: readonly и целевые наборы
**What:** `readonly` на владеемом поле (по сохранённому состоянию владельца) замораживает состав строк — добавление, удаление, исключение из `PUT …/links`, прямое архивирование строки отклоняются; значения строк подчиняются правилам самой строки; архивирование владельца разрешено. Живая строка в любом сохранении (пакет или прямой `PATCH`) сохраняет один из `target_sets` своего поля.
**Why:** В подпроекте 1 `readonly` на поле-ссылке замораживает её цели; без этого правило обходилось бы пакетом и прямым архивированием. Единая проверка целевого набора убирает расхождение между пакетом и прямой правкой.
**Affected:** spec §1.12, packages/db/src/service/rows.ts, record-service.ts

## 2026-10-31 — Системные наборы встроены в код, YAML их расширяет
**What:** Наборы `contact`, `organization`, `membership` (и позже `conversation`, `task`) и их поля поставляются пакетом `core` как системная часть конфига, загружаемая первой. Пользовательский YAML расширяет их секцией `extend` (свои поля в набор, `label`/`options` системного поля); объявить системный ключ, сменить тип/цели/кардинальность системного поля или убрать его из набора — ошибка старта. Служебные поля (`managed`) пишет только код.
**Why:** Код опирается на конкретные системные поля; конфиг (в будущем — конфиг SaaS-клиента) не должен иметь возможности сломать сопоставление и слияние. Новый workspace получает рабочие контакты без копирования шаблона.
**Affected:** spec §3, 2026-10-31-contacts-organizations-design.md §2.1

## 2026-10-31 — Владелец адреса: контакт, участие или организация; WhatsApp = телефон
**What:** Адрес канала (email, телефон, Telegram) принадлежит контакту (личный), его участию в организации (адрес в роли) или организации (адрес фирмы без закреплённого человека). При уходе из организации адреса и связи участия передаются преемнику, на организацию, с человеком или остаются как история. Семья частного клиента — запись `organization` с `org_kind = "частный клиент"`. WhatsApp не отдельный канал адресов — ищется по `phone`.
**Why:** Рабочий номер бухгалтера может остаться у фирмы или уйти с человеком — оба случая реальны; адрес на участии сразу даёт и человека, и контрагента. Отдельная «должность» (третий уровень) отвергнута как избыточная для 1–3 пользователей; пустые контакты-заглушки — как засоряющие базу.
**Affected:** spec §3.1–3.3, 2026-10-31-contacts-organizations-design.md §3–§5

## 2026-11-01 — Поведение системных наборов: четыре точки в конвейере сохранения
**What:** Код системного набора подключается к `RecordService` через `SetBehavior`: `beforeInsert` (до первой вставки записи на создании), `beforeEvaluate` (до вычисления, может поправить ввод), `afterWrite` (после записи значений, наборов и связей, до каскада) и `archived` (после архивирования), плюс `extendView`. Несколько сохранений одной операции (передача дел, слияние) идут через `RecordService.transaction` с одним каскадом.
**Why:** Создание сохраняет сырой ввод до вычисления (строки 1b видят сохранённые значения владельца), поэтому нормализация и уникальность NIP должны предшествовать вставке; ограничения участия зависят от связей и проверяются после их записи.
**Affected:** packages/db/src/service/behaviors.ts, record-service.ts, contacts/*

## 2026-11-01 — setLinks проверяет только новые цели поля
**What:** При сохранении связей существование, архивность, целевые наборы и циклы проверяются только у целей, которых у поля ещё не было; количество — по всему списку; владеемые поля — полная проверка `link_owned`.
**Why:** Связи на архивные записи остаются историей (§1.12); повторная проверка старых целей блокировала слияние и передачу дел, как только запись ссылалась на архивную.
**Affected:** packages/db/src/service/record-service.ts (`linkErrors`)

## 2026-11-01 — Нормализованные имена хранятся в record_search
**What:** Нормализованные ФИО, названия фирм (без правовой формы) и адреса организаций хранит таблица `record_search`, её пишет поведение наборов `contact`/`organization`; кандидаты в дубли ищутся `pg_trgm` по ней. Нормализация — одна функция `@icrm/core`, её же использует импорт для поиска организации по названию.
**Why:** Одна реализация нормализации вместо двух (JS и SQL через `unaccent` с самодельной неизменяемой обёрткой), которые неизбежно разошлись бы.
**Affected:** spec 2026-10-31-contacts-organizations-design.md §7.1, §8; packages/db/src/repo/search.ts

## 2026-11-01 — Импорт: пробный прогон без записи, коммит построчно
**What:** Пробный прогон строит план чтением с наложением того, что создали бы предыдущие строки файла; коммит перепланирует каждую строку по текущей БД и выполняет её в своей транзакции. Организация по названию совпадает, только если у неё NIP пуст или равен NIP строки. Значение перечисления вне вариантов — предупреждение. Строка без адресов при повторном импорте создаётся снова (с предупреждением).
**Why:** Пробный прогон не должен менять данные и должен совпадать с записью; одна ошибочная строка не должна останавливать остальные; две фирмы с одним названием и разными NIP — разные фирмы.
**Affected:** packages/db/src/contacts/import.ts, import-plan.ts

## 2026-11-01 — Импорт за Cloudflare Tunnel: решить до развёртывания
**What:** Коммит импорта синхронный; 5000 строк занимают минуты и не укладываются в таймаут прокси Cloudflare (100 с). До развёртывания выбрать: фоновая задача импорта на pg-boss с опросом результата или ограничение/разбиение коммита.
**Why:** Поведение импорта верное, мешает только таймаут прокси; worker с pg-boss ещё не создан.
**Affected:** apps/server/src/routes/import.ts, будущий apps/worker
